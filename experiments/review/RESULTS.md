# Reviewer analyses — results

Two analyses requested by the thesis reviewer, run 2026-11-15 UTC. Every number below
is copied from the file named under its table. Nothing was retrained or rerun for
Run B, Run C or Run T, and no protected file changed (68 SHA-256 hashes identical
before and after; `results/protected_sha256_{before,after}.txt`). Commands, seeds,
versions and decisions are in `RUN_LOG.md`.

Abbreviations: F1 = macro F1; FPR = benign events predicted as any attack / benign
events; FNR = attack events predicted benign / attack events (as `pipeline.detect.evaluate_split`).

## Analysis 1 — Permuted-context control for the Run B ablation

**Question.** In the Run B ablation, `event_plus_incident` scored slightly higher macro F1
than `event_only` (and had a higher FPR). Is that due to the link between an event and its own
incident, or only to the extra columns and their distribution?

**Control.** `event_plus_permuted_incident` uses the 20 event features plus `n_events`,
`span_s` and `events_per_s`. The three incident columns are shuffled together as whole
rows across events, within each (partition, source) stratum, without using labels.
Train and test are shuffled separately, and the shuffle seed equals the model seed.
Everything else comes from `experiments/ablation/run_ablation.py`, imported unchanged:
the same RF settings (300 trees, depth 24), the same 196,406 training events per seed and
the same 1,692,332 Run B test events.

**Reproduction gate (passed).** Before the grid ran, seed 42 `event_only` and
`event_plus_incident` at 300 s matched `experiments/ablation/results/full/ablation_results.csv`
in all 5 subsets and all metrics, at tolerance 1e-12 (`results/permuted_context/checks.json` →
`reproduction`). After the run, all 30 rerun `event_only`/`event_plus_incident` runs
(150 rows) also matched exactly (`results/permuted_context/full_reproduction.json`).

### 1c. Shuffle checks

- In every one of the 25 (window, seed) shuffles, the multiset of incident-feature values was identical
  before and after within train and within test (`checks.json` → `permutation`).
- **The link is only partly broken.** After shuffling, 18.1% (60 s) to 33.9% (300–900 s) of test events,
  and 17.4%–27.0% of training events, still have exactly their own (n_events, span_s, events_per_s)
  values (`checks.json` → `test_rows_equal_to_own_context`, `train_rows_equal_to_own_context`).
  This happens because many events share identical values in the same source, for example singleton
  incidents (1, 0, 0) and the large Bot-IoT floods. A shuffle that keeps the distribution cannot
  change these rows.

### 1d. What the results show

1. **True context does better than permuted context on macro F1.** It is higher at every window
   (point +0.0015 to +0.0040). The interval excludes 0 at 60, 150, 300 and 900 s and just
   includes 0 at 600 s. So the small F1 gain from incident context depends on the event–incident
   link, not only on the extra columns.
2. **Permuted context does not help on its own.** Against `event_only`, its macro F1 is no higher
   at any window. It is lower at 300, 600 and 900 s (intervals exclude 0); at 60 and 150 s the
   intervals include 0.
3. **This result goes against the thesis direction: most of the FPR increase is present without the
   link.** `event_only` FPR is 0.38%. With permuted context, FPR is 0.95%–1.05% (+0.47 to +0.62 pp,
   all intervals exclude 0). With true context, FPR is 1.13%–1.18%, a further +0.07 to +0.24 pp
   (all intervals exclude 0). Most of the extra false positives from adding incident features
   therefore come from the presence and distribution of those columns, not from the correct incident link.
4. **Caveats.**
   - The shuffle stays within a source, so the permuted columns still carry source-level information.
     Several sources are nearly single-class.
   - 18%–34% of events keep their own values (1c).
   - The bootstrap uses seed 42 only.
   - 600 s and 900 s contexts are cut at the partition boundary.
   - All differences in macro F1 are below 0.005.

## Analysis 2 — Run T boundary sensitivity

**Run T found** at `../thesis_final_validation/supplementary_temporal/` (outside the repository). Not blocked.

**Definition.** Run T cuts each source at its 75th timestamp percentile and appends the split side to the
correlation key. A conversation group that spans the cut therefore becomes two incidents. A test event
is a *boundary event* when its group key without the split suffix (source, rule, src/dst/proto, 300 s
bucket; `pipeline.correlate.correlation_key`) also has training events. *Boundary incidents* are the
test-side incidents of those groups. A broader secondary definition, the same flow on both sides of the
cut in any time bucket, is reported separately below.

**Checks (all passed, `results/boundary/checks.json`).**
- The prediction rows line up with the Run T event table on source, incident, split and label.
- The recomputed all-event metrics equal Run T `stage5_report.json`.
- Split-free groups give 704,090 (= Run B incidents). With the split side they give 704,151 (= Run T
  incidents). So exactly **61 groups were cut**.

### 2c. What the results show

1. **The boundary groups explain most of the integrated accuracy drop, but not the F1 or FPR gap.**
   - Excluding the 61 boundary incidents raises integrated accuracy from 0.7155 to 0.9480.
   - FPR is essentially unchanged (9.65% → 9.62%). The benign → recon errors (10,969 of 12,036)
     are not boundary effects.
   - The fragmented baseline is unchanged at 0.9981–0.9992 F1 and 0.44% FPR.
   - The integrated − fragmented gap therefore remains: F1 −0.299, FPR +9.2 pp on the subset.
2. **Macro F1 for the integrated model goes down, not up (0.7711 → 0.6994).**
   - Excluding boundary groups removes 491,358 of 503,405 DoS test events.
   - The 12,047 DoS events that remain come from 6 test-only incidents, 11,912 of them in data_10.
     The integrated model predicts 12,045 of them as recon, so DoS F1 is 0.0 on the subset
     (`per_class.json`).
   - So the DoS → recon failure is not limited to incidents the cut split: short test-side DoS
     incidents that were not cut fail the same way.
   - Macro F1 on this subset averages five classes with very different support from the full test
     set, so it is not directly comparable with the all-event value.
3. **Within the boundary groups the fragmented baseline is near-perfect** (accuracy 1.0000), while
   the integrated model gets 0.4622 (270,855 DoS predicted recon). This is consistent with the
   cut-artefact explanation in Run T `RESULTS.md` §4.3.
4. **The secondary, broader definition removes 73% of test events,** leaving only 135 DoS and 1 c2
   event. Its macro F1 values reflect those near-empty classes (fragmented DoS F1 0.0) and should not
   be used as a headline.
5. **Limitations.**
   - Excluding events changes the class mix.
   - Run T is one seed and one configuration.
   - The analysis uses saved predictions, so the model was still trained with the cut-affected training
     incidents.
